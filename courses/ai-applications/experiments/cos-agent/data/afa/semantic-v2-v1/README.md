# v2 첫 단계 — 의미·응답·중단 계약

해당 버전의 실험 기록이다. 현재 에이전트에서 AFA가 맡는 역할은 [목표 구조](../../../docs/agent-runtime-target.md)를 참고한다.

목적: **같은 사용자 상태에서 질문 순서만 바뀌었다고 최종 권고의 의미가 바뀌지 않도록 한다.** 현재 엔진의 분기 우선순위를 유지하면서, 어떤 정보가 있어야 그 결과를 확정할 수 있는지 별도 계약으로 명시한다.

상태: **합성 개발용 의미 계약과 실행 검사 완료.** v2 Gym 환경·데이터 분할·보상·학습·독립 도메인 검토는 아직 없다. 기존 v1 결과와 원본 KB는 변경하지 않는다. 이 계약은 전문가 검토·서비스 정책 승인을 대신하지 않는다.

## 숲: 전체 흐름과 현재 작업

v1 시험 학습 완료 → **현재: v2 의미 계약** → v2 범위·응답 세계·비용·분할 설계 → adapter·환경 구현 → 환경 검증·기준선·개선 여지 확인 → 비교 학습 → 독립 평가.

이번 산출물은 `contract.json`, `beauty_agent/afa/semantics.py`, `tests/test_afa_semantics.py`다. 다음 단계의 데이터 생성기와 환경이 따라야 할 의미를 먼저 고정한다. 여기서 범위를 크게 넓히거나 기존 학습기에 v2를 자동 연결하지 않는다.

## 1. 결정: 기존 첫 매칭 분기의 의미를 유지한다

검토한 선택지는 ① 서로 다른 권고를 동등하다고 처리, ② 여러 권고를 합쳐 새 결과 생성, ③ 기존 우선순위를 유지하고 결과를 구분할 정보를 더 확인하는 방법이다. 이번 기술 계약은 **③**을 채택한다.

①은 `inform_general_practice`와 `suggest_behavior_change`를 임의로 같은 정답으로 만들고, ②는 원본에 없는 권고 조합을 만든다. ③은 현재 스냅샷의 판정 의미를 보존하면서 질문 순서로 생기는 불일치를 해결한다. 이것은 첫 매칭 정책이 도메인 관점에서 최선이라는 승인이 아니다. 그 정책 자체를 바꾸려면 별도의 KB 버전·검토·회귀 기록이 필요하다.

### 문제를 구체적으로 보기

숨겨진 전체 상태에 도구 차이와 강한 마찰이 모두 있다고 하자.

| 확인한 공개 정보 | 원본 엔진에서 보이는 결과 | 이번 계약의 판단 |
| --- | --- | --- |
| 부위만 face | 추가 정보 필요 | 세부 질문을 확인 |
| 마찰 strong 추가 | `suggest_behavior_change`, 기존 초안 게이트가 열릴 수 있음 | tools가 hands일 때와 scrub_brush일 때 최종 action이 달라짐. **아직 초안 확정 불가** |
| tools=scrub_brush 확인 | 앞 분기의 `inform_general_practice` | 다른 미확인 슬롯이 바뀌어도 최종 의미가 같으면 확정 가능 |
| tools=hands 확인 | `suggest_behavior_change` | 마찰 strong으로 최종 의미가 고정되면 확정 가능 |

따라서 **마찰부터 물은 경로에 tools 확인을 추가**한다. 모든 슬롯을 무조건 묻는 방식은 아니다. tools=scrub_brush가 먼저 확인되면 마찰·건조가 남아도 최종 의미가 이미 고정될 수 있다.

## 2. ‘결과 확정 가능’의 정확한 정의

1. 공개적으로 확인된 known 값만 고정한다.
2. 아직 알 수 없는 슬롯은 사전에 선언한 유한 합성 domain의 모든 값으로 완성해 본다.
3. 각 완성 상태를 **변경하지 않은 엔진**으로 평가한다.
4. 가능한 결과의 의미 서명이 하나이고 현재 결과도 그것과 같을 때 semantic certificate가 성립한다.
5. 초안에는 certificate 외에도 **기존 runtime 초안 게이트 통과·필수 정보 충족·필수 보류 없음**이 모두 필요하다.

비교하는 의미는 카드별 comparison_status·action_types·recommendation_text와 전체 hold_signals·overall이다. branch ID와 reason은 추적 정보이며 일치 조건이 아니다. action이나 보류 의미가 다른 결과는 합치지 않는다. 카드 목록을 정렬해 입력 배열 순서가 의미를 바꾸지 않게 한다.

이는 실제 숨겨진 세계나 미래 답을 읽는 oracle이 아니다. `inspect(cards, ledger)`는 공개 이벤트만 받는다. 모든 완성 상태를 검사하는 것은 선언된 domain에서의 보수적 기술 증명이다. domain이 현실의 모든 값을 포함한다는 보장은 없으며, 실제 사용·도메인 안전성·평가 정답의 증명이 아니다. train 빈도에 따른 확률이나 사용자 특성을 추정하지 않는다.

## 3. 질문 후보 계약과 기존 런타임의 경계

슬롯 하나만 바꾸고 다른 완성 값은 고정했을 때 의미가 달라질 수 있으면, 그 슬롯을 결과 구분에 필요한 정보로 본다. 기존 런타임 질문과 함께 검사하되 다음을 적용한다.

- body_site를 먼저 확인하는 기존 앞단 게이트 유지.
- 이미 답한 known/unknown/declined/conflicting 슬롯은 같은 episode에서 자동 재질문하지 않음.
- 충돌·필수 보류가 있으면 초안을 내지 않음.
- 명시적인 필수 정보가 미확인이면 의미가 안정적이어도 초안을 내지 않음.
- 제품 정보는 사용자 질문으로 채우지 않음.

**중요한 구현 차이:** 원본 PreviewEngine은 마찰 분기가 매칭되면 tools 질문을 닫을 수 있다. 이번 검사기의 `research_question_requirements`에 tools가 있어도 기존 `ActionContext`에서 실행 가능한 행동이 된 것은 아니다. `adapter_extension_required`가 그 차이를 표시한다.

다음 환경 단계에서 KB의 consumer_question_allowed·원문 질문·조건을 검증한 **별도 버전의 v2 질문 adapter**를 구현해야 한다. 현재 Context/validate_action 마스크를 몰래 넓히지 않는다. 이번 코드는 `decide_action`/dispatch를 호출하지 않고 실제 질문 문구나 권고를 새로 생성하지 않는다.

## 4. 모름·거절·충돌·정정

| 입력 상태 | 저장 의미 | 다음 판단 |
| --- | --- | --- |
| 미질문 | ledger에 이벤트 없음 | body_site·결과 관련성 조건을 만족하면 질문 가능 |
| known | 확인된 domain 내 값 | 해당 값으로 가능한 상태를 제한 |
| unknown | 답했지만 모름, value=null | false/기본값으로 바꾸지 않음. 자동 재질문하지 않음 |
| declined | 답변 거절, value=null | 동의한 것으로 바꾸지 않음. 자동 재질문하지 않음 |
| conflicting | 충돌 보존, value=null | 초안 차단. 기존 충돌 해결 흐름의 adapter 연결은 다음 단계 |
| 명시적 정정 | 새 이벤트가 이전 event_id를 supersedes | 최신 공개 상태를 다시 계산하고 준비 token 무효화 |

이벤트는 `event_id`, `ObservationSlot`, `supersedes`로 구성한다. 이번 범위는 confirmed synthetic_fixture만 받는다. 자동 추출 후보를 확인된 관찰로 바꾸지 않는다. 기록은 순서대로 적용하며, 뒤의 정정을 첫 턴 값으로 합치지 않는다. 중복 ID·묵시적 값 교체·오래된 이벤트를 supersedes하는 교체는 오류다.

예를 들어 `tools1=scrub_brush` 뒤 `tools2=hands, supersedes=tools1`이 오면 tools1 기록을 남긴 채 현재 값만 hands로 바뀐다. 이전 준비 token으로 실행하려 하면 stale 오류가 나야 한다. 실제 SessionState 커밋·정정 dispatch 연결은 아직 구현하지 않았다.

## 5. 중단·보류와 필수 정보

| 상황 | 계약상 다음 상태 |
| --- | --- |
| 기존 runtime 필수 안전 보류 발생 | mandatory_hold가 우선. 초안 차단 |
| 공개 관찰 충돌 | conflict_hold. 임의 known 값으로 해결하지 않음 |
| certificate + runtime gate + 필수 정보 모두 충족 | draft_ready |
| 결과 구분 또는 필수 정보 획득 질문이 남음 | needs_information |
| 필요한 답을 모름/거절했고 더 진행할 수 없음, 또는 기존 gate가 닫힘 | insufficient_information_hold |

**모든 미확인 정보가 필수 정보는 아니다.** tools 차이로 결과가 고정되고 별도 필수 슬롯이 없다면, 관련 없는 마찰 정보의 거절만으로 추가 질문을 만들지 않는다. 반대로 필수 정보는 결과 서명에 영향이 없어도 생략할 수 없다.

현재 `required_slots=[]`이며 새로운 임상 안전 질문 목록을 발명하지 않았다. C01/C02 범위를 넘어선 안전 카드·억제 카드·필수 안전 필드의 매핑과 종합 경로 검사는 다음 범위 설계에서 결정해야 한다. 이번 코드가 전체 에이전트의 안전 보류를 검증했다고 표현하지 않는다.

이 단계는 중단 가능한 조건의 의미만 정의한다. 보류의 정오·미제공 손실·모름/거절 비용·사용자 피로·통계 성공 기준은 별도의 v2 보상·평가 protocol에서 결과 열람 전에 정한다. 모름을 외부 truncation으로 바꾸지 않는다. 마지막 답 뒤 정당한 무료 종료와 외부 TimeLimit 구분은 기존 계약을 보존한다.

## 6. 범위와 검사 결과

실행 검사의 값 범위는 v1이 이미 선언한 C01/C02 합성 domain을 사용한다. 단일 카드 19개 완성 세계를 모두 검사하고, 세부 질문 우선순위 99개를 순회한다. 같은 실제 질문 경로로 합쳐지는 우선순위도 있으므로 **99개 독립 사례/고유 경로가 아니다**.

기존에 제외한 혼합 의미 세계 9개에서도 54개 질문 우선순위 모두 원본 full-information 의미로 끝나는지 확인한다. 이는 domain 안에서 추가 정보 계약이 불일치를 해결한다는 기계 검사다. 9개 세계를 사람 정답으로 승인하거나 기존 v1 train/val/test에 편입하지 않는다.

추가 검사는 unknown/declined 재질문 금지, 불필요한 거절의 처리, conflict 차단, 정정·stale token, domain 밖 사실·제품 입력 거부, C01+C02 공동 서명, 명시한 필수 정보의 생략 금지를 다룬다. 공동 카드 검사는 작은 의미 검사이며 다중 카드 Gym 환경 구현 완료가 아니다.

`cos-agent/`에서:

```powershell
uv run --locked --group rl-train python -m beauty_agent.afa.semantics --report ../../../../outputs/afa-v2-semantics-v1/report.json
uv run --locked --group rl-train pytest -q tests/test_afa_semantics.py
```

기본 Python 검사만으로도 실행 가능하며 Gym/Torch를 import하지 않는다. 위 group은 기존 학습 가상환경의 패키지 구성을 유지하려고 명시했다. 출력은 새 경로만 허용하고 원본 KB·v1 보고서·학습 모델은 덮어쓰지 않는다.

## 다음 단계의 입력과 완료 조건

이번 계약을 입력으로 **v2의 첫 카드 범위·필수 정보·응답 시나리오·비용·계보/분할 계획**을 작성한다. 그다음 질문 확장 adapter와 이벤트 기반 환경을 구현한다. 다음 사항이 충족되기 전에는 v2 학습 준비 완료라고 부르지 않는다.

- 관련 카드와 domain의 범위·제외 조건 및 필수 정보 매핑 동결
- 질문 확장·정정·충돌·보류를 기존 실행 게이트와 연결한 adapter 구현
- 관련 슬롯의 응답표와 모름/거절/정정 이벤트·출처 완비
- v67 원본/합성 보완 구분, 부모 계보·가족 단위 분할·비용·평가 계획 동결
- 환경 전수/경계 검사, 강한 기준선 비교와 실제 개선 여지 확인

독립 도메인 검토는 계속 `human_review=unreviewed`, `approved_reference=false`다. 사용자 데이터 수집·실사용·제품 근거 승인·앱 연결은 활성화하지 않는다.
