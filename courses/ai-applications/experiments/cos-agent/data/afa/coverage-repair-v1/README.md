# 평가 상황 보완 — 빠졌던 손세안을 포함하기

해당 버전의 실험 기록이다. 현재 에이전트에서 AFA가 맡는 역할은 [목표 구조](../../../docs/agent-runtime-target.md)를 참고한다.

**학습·내부 확인·내부 테스트에 손세안과 도구 사용 상황이 모두 들어가도록 별도 버전을 만들었습니다.** 기존 자료와 결과는 그대로 보존했습니다. 이번에는 PPO 학습이나 정책 성능 비교를 하지 않았습니다.

## 왜 바꿨나?

기존 내부 확인·테스트에는 도구 사용 상황만 있었습니다. 도구 답으로 세안 방법의 결론이 빨리 정해지는 사례 위주라, 손으로 씻으며 마찰·건조까지 확인해야 하는 경우가 빠져 있었습니다.

이번에는 **모델 점수가 아니라 입력 상황의 종류**를 기준으로 묶음을 나눴습니다. 같은 세안 방법에서 물 온도만 다른 사례들은 여전히 같은 묶음에 둡니다.

| 자료 | 전체 상황 수 | 기존 손세안 상황 | 새 버전 손세안 상황 |
| --- | ---: | ---: | ---: |
| 학습 | 30 | 12 | **6** |
| 내부 확인 | 9 | 0 | **3** |
| 내부 테스트 | 9 | 0 | **3** |

나머지는 도구 사용 상황입니다. 모든 묶음에 세 물 온도 값도 포함합니다. 손세안은 추가 조건이 필요할 수 있는 구조적 분류이며 사람이 평가한 난도·임상 라벨이 아닙니다.

**새 사용자나 답을 만든 것이 아닙니다.** 이미 살펴본 48개 가상 상황의 배치만 이 별도 버전에서 바꿨습니다. 24개 상황의 소속이 달라졌지만 원래 소속을 `prior_split`에 남겼습니다. 실제 답·참조·부모/가족 ID·질문 비용·안전 게이트·기존 KB는 유지했습니다.

## 한 번 나누는 것만으로는 해결되지 않는 문제

현재 세안 방법 조합은 16묶음입니다. 그중 손세안은 4묶음이고, 손·부드러운 마찰·가볍게 두드리는 건조가 모두 맞는 조합은 **1묶음**입니다.

- 그 1묶음을 학습·확인·테스트에 모두 복사하면 같은 문제를 양쪽에서 쓰는 셈입니다.
- 한 묶음에만 두면 다른 두 묶음에서는 그 유형을 확인할 수 없습니다.
- 도구 종류는 4개인데 확인·테스트는 각각 3묶음뿐이라, 모든 도구 종류를 각각에 넣는 조건도 불가능합니다.

검사기는 이 제약을 보고서에 명시합니다. 새 고정 분할은 두 큰 유형의 누락을 보완했지만 모든 세부 유형의 완전한 평가를 보장하지 않습니다. 새 버전에서도 모든 기본 사용법이 맞는 손세안 조합은 train 한 곳에만 있습니다. 이 사실을 숨기거나 복제본을 독립 사례로 만들지 않았습니다.

## 빠진 유형까지 확인하기 위한 별도 순환 점검 계획

`fold-plan.json`에는 **16개 세안 방법 묶음을 하나씩 번갈아 확인 대상으로 빼는 계획**을 만들었습니다.

1. 한 세안 방법 묶음의 3개 상황을 확인 대상으로 뺍니다.
2. 나머지 45개만 준비·학습에 사용할 수 있습니다.
3. 같은 설정으로 빠진 3개를 확인합니다.
4. 확인 대상을 바꾸고 처음부터 새로 준비합니다. 총 16번입니다.

이렇게 하면 모든 유형이 한 번씩 확인 대상이 됩니다. 하나뿐인 조합도 해당 차례에서는 준비 자료에 들어가지 않습니다. **매 차례는 서로 다른 모델/분포 추정을 새로 만들어야 하며 이전 모델을 이어 쓰면 안 됩니다.** 확인 결과 전체를 보고 설정을 고르는 것도 허용하지 않습니다. 조정이 필요하다면 내부 준비 자료 안에서 별도 계획이 필요합니다.

이번에 만든 것은 이 일정과 중복 방지 검사입니다. 16번의 모델 학습·성능 측정을 실제로 수행한 것은 아닙니다. 공통 학습량·설정·seed·모델 선택 규칙도 실행 전에 별도로 고정해야 합니다.

차례가 바뀌면 같은 사례가 다른 차례의 준비 자료에 들어갈 수 있습니다. 이것은 순환 점검의 구조이며, 각 차례 안에서는 확인 가족과 준비 가족이 겹치지 않습니다. 새롭거나 독립적인 실제 사용자 평가가 된다는 뜻은 아닙니다.

## 지금 사용할 수 있는 것

| 파일 | 역할 |
| --- | --- |
| `partition.json` | 손세안/도구 사용의 고정 배정 수와 선택 기준 |
| `train.jsonl`, `val_internal.jsonl`, `test_internal.jsonl` | 같은 48개 답변의 새 내부 배치. 원래 소속과 출처 보존 |
| `manifest.json` | 새 파일·생성 코드·기존 원본의 해시와 가족 배정 |
| `fold-plan.json` | 16회 순환 점검의 준비/확인 대상 ID 및 모델 분리 조건 |

현재 실행 환경은 별도 bundle 경로를 지정하면 이 자료를 읽습니다. 새 확인·테스트의 손세안 상황이 기존 환경에서 초기화·질문·정상 종료되는 것을 소프트웨어 검사로 확인했습니다. 이 점검을 정책 성능 평균으로 집계하지 않았습니다.

기존 비교 프로그램은 계속 원래 v2 자료를 기본으로 사용합니다. 새 자료로 본 비교를 할 때는 준비 자료와 실행 환경이 모두 이 새 bundle을 명시적으로 사용하도록 별도 실행 절차를 연결해야 합니다. 새 분포를 만들고 옛 자료에 평가하거나, 옛 모델을 이어 쓰는 혼합을 피해야 합니다.

## 무엇이 아직 끝나지 않았나?

- 실제 사용자가 아닌, 이미 점검한 같은 합성 제품·규칙·상황입니다. 새 분할을 독립 최종 평가라고 부르지 않습니다.
- 모름·거절·정정은 기존 공개 점검 예시로 남아 있습니다. 이를 성능 자료에 넣으려면 실제 공개 응답 중복과 정정 부모 관계까지 함께 묶어야 합니다.
- 독립 제품/규칙 가족·외부 참조·사람 검토는 아직 없습니다.
- 기존 v67을 변환하거나 학습에 사용하지 않았습니다.
- 구성을 보완해도 작은 문제에서 정확한 계산 방식이 이미 최적일 수 있습니다. PPO가 더 적게 묻도록 보장하거나 비용·정답 조건을 유리하게 바꾸지 않았습니다.

**다음에는 이 순환 점검에 사용할 공통 비교 설정을 고정하고, 각 차례에 준비 자료가 섞이지 않도록 실행 코드를 연결할 수 있습니다.** 그 후에야 기존 방식의 새 결과를 측정합니다. 정책 학습이나 일반화 주장은 그 결과와 더 넓은 과제 설계를 바탕으로 별도 판단합니다.

## 재현과 검사

`cos-agent/`에서:

```powershell
uv run --locked --group rl-train python -m beauty_agent.afa.coverage_repair verify --report ../../../../outputs/afa-coverage-repair-v1/coverage-recheck.json
uv run --locked --group rl-train python -m beauty_agent.afa.coverage_folds verify --report ../../../../outputs/afa-coverage-repair-v1/fold-recheck.json
uv run --locked --group rl-train pytest -q tests rl_tests ppo_tests
```

최초 생성만 각각 `build`를 사용합니다. 기존 자료와 보고서는 덮어쓰지 않습니다. 배정은 고정 문자열과 가족 ID의 SHA-256 순서를 사용하며 보상·기존 성능·PPO 출력은 사용하지 않습니다. 같은 부모와 실제 응답표가 한 차례의 서로 다른 묶음에 겹치면 오류로 처리합니다.

`development_preview`, `production_enabled=false`, `human_review=unreviewed`, `approved_reference=false`, `independent_evaluation=false`를 유지합니다.
