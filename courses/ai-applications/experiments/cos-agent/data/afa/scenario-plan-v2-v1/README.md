# 다음 연습장 설계 — 무엇을 묻고, 어떻게 비교할 것인가

해당 버전의 실험 기록이다. 현재 에이전트에서 AFA가 맡는 역할은 [목표 구조](../../../docs/agent-runtime-target.md)를 참고한다.

**이번에 한 일은 더 넓은 연습장의 설계와 예시 점검입니다. 아직 새 학습을 돌리지는 않았습니다.**

현재까지는 작은 연습장에서 PPO 학습이 작동하는지 확인했습니다. 이제 물 온도와 세안 방법을 함께 다루는 상황으로 넓힙니다. 목표는 **안내 수준을 유지하면서 어떤 질문을 먼저 물으면 부담을 줄일 수 있는지** 비교하는 것입니다. [기존 결과](../stage5a-trial-v1/README.md)는 그대로 보존합니다.

## 1. 이번에 정한 네 가지

| 질문 | 이번 결정 |
| --- | --- |
| 무엇을 물을까? | 적용 부위, 물 온도, 세안 도구, 마찰, 건조 방법. 한 상황에서 물 온도와 세안 방법을 함께 검토 |
| 어떤 연습 상황을 만들까? | 답이 모두 정해진 가상 상황 48개. 모름·거절·충돌·정정은 별도 점검 예시 9개 |
| 질문 부담을 어떻게 셀까? | 기본은 질문마다 1점. 별도 비교에서는 마찰·건조 질문을 2점으로 계산 |
| 학습과 확인 자료는 어떻게 나눌까? | 세안 방법 조합 16묶음을 먼저 나눔. 학습 30개, 내부 확인 9개, 내부 테스트 9개 |

모든 값은 **합성 실험 설계**입니다. 실제 사용자, 제품 성능, 피로 측정, 전문가 정답이 아닙니다. 세안 방법별 규칙 묶음은 코드에서 B-C01·B-C02라는 카드 ID로 관리합니다. 기존 규칙 내용은 바꾸지 않습니다.

## 2. 연습 상황의 모습

가상 사용자가 “얼굴을 뜨거운 물로 씻고, 손으로 부드럽게 씻으며 가볍게 두드려 말린다”고 설정합니다. 에이전트에게 처음부터 이 답을 모두 주지 않습니다. 질문한 항목의 답만 돌려주는 환경을 다음 단계에서 구현합니다.

- 물 온도: cold / lukewarm / hot의 기존 합성 domain
- 도구: hands / scrub_brush / washcloth / sponge
- 마찰: gentle / strong
- 건조: pat_gently / rubbing_strongly
- 부위: face로 설정하되, **공개 입력으로 자동 확정하지 않고 먼저 확인**

3 × 4 × 2 × 2 = **48개**입니다. 현재 검사기는 이 조합의 설계 목록을 생성합니다. 실제 질문/응답이 실행되는 학습용 파일이나 Gym 환경은 아직 아닙니다.

지난번 정한 [의미 계약](../semantic-v2-v1/README.md)을 유지합니다. 예를 들어 마찰 답만으로 결론을 내렸더라도, 도구 답에 따라 안내 의미가 바뀔 수 있으면 더 확인해야 합니다. 반대로 남은 답을 알아도 안내가 달라지지 않으면 불필요한 질문을 생략할 수 있습니다.

## 3. 까다로운 답변은 별도 점검부터

`probes.json`의 9개 예시는 다음을 점검합니다.

| 예시 | 확인한 동작 |
| --- | --- |
| 필요한 답을 모두 제공 | 정해둔 기준에 맞으면 초안 가능 |
| 도구 답으로 결과가 이미 정해짐 | 관련 없는 마찰·건조를 더 묻지 않음 |
| 마찰을 먼저 답함 | 도구 확인이 더 필요할 수 있음 |
| 필요한 도구 답을 “모르겠다” | 값을 추정하지 않고 보류 |
| 필요한 도구 답변을 거절 | 자동 재질문하지 않고 보류 |
| 결과와 무관한 마찰 답변을 거절 | 불필요한 질문을 추가하지 않음 |
| 입력이 서로 충돌 | 임의로 하나를 골라 안내하지 않음 |
| 도구 답을 명시적으로 정정 | 이전 답을 기록에 남기고 다시 판단 |
| 적용 부위 답변을 거절 | 세부 세안 질문으로 넘어가지 않음 |

이 9개는 **공개된 소프트웨어 점검 예시**입니다. 학습이나 정책 성능 점수에 넣지 않습니다. 모름·거절을 포함한 본격적인 학습 자료는 이후 별도 설계합니다.

분리한 이유도 있습니다. 서로 다른 숨겨진 도구 값을 가진 두 상황이 모두 “도구를 모르겠다”고 답하면, 에이전트 입장에서 같은 응답표가 될 수 있습니다. 이런 자료를 학습과 테스트에 나누면 같은 문제를 양쪽에 넣는 셈입니다. 이번 버전은 먼저 가계도와 실제 공개 응답의 중복 검사부터 마련하고, 정정·모름 예시를 임의로 여러 split에 섞지 않습니다.

## 4. 질문 비용과 종료 기준

| 실험 조건 | 부위 | 물 온도 | 도구 | 마찰 | 건조 | 최대 질문 비용 | 잘못 끝낸 경우 추가 손실 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 기본 비교 | 1 | 1 | 1 | 1 | 1 | 5 | 6 |
| 비용 변화 확인 | 1 | 1 | 1 | 2 | 2 | 7 | 8 |

마찰·건조의 2점은 **실험용 가정**입니다. 실제로 두 배 힘들다는 뜻은 아닙니다. 기본 비교는 모두 1점으로 하고, 비용을 다르게 줬을 때 결과가 달라지는지 별도로 확인합니다.

- 최대 질문은 5회. 답이 모름·거절이어도 실제 물었다면 비용을 셉니다.
- return은 질문 비용과 잘못된 종료 손실의 음수 합입니다. gamma=1, shaping=0.
- 초안은 의미 확정 조건과 기존 실행 게이트를 모두 통과해야 합니다.
- 정상 보류는 기존 전체 정보 판정이 보류이고, 지원 질문이 더 남지 않은 경우입니다. 기존 cold 응답의 미해결 처리를 임의로 정상 초안으로 바꾸지 않습니다.
- 마지막 답 뒤에 정당한 초안·보류를 선택하는 데 별도 질문 비용을 붙이지 않습니다.
- 예산 부족으로 끝난 것과 외부 시간 제한으로 끊긴 것을 구분합니다.
- 품질·안내 제공 수준을 낮추고 질문만 줄이면 개선으로 인정하지 않습니다.

이번 조건은 **질문 순서 최적화**를 위한 것입니다. 불확실한 상황에서 질문 비용과 오판 위험을 저울질하는 중단 학습 전체를 해결한 것은 아닙니다. 모름·거절의 효용·미제공 손실 등은 아직 본 성능 평가 protocol에 포함하지 않습니다.

## 5. 자료 나누기: 같은 가족은 함께

도구 × 마찰 × 건조의 16개 조합을 가족으로 묶습니다. 같은 세안 방법에서 물 온도만 다른 3개는 같은 가족입니다. 먼저 가족을 나누고, 그 안의 모든 상황이 같은 split을 상속합니다.

| 용도 | 가족 수 | 가상 상황 수 |
| --- | ---: | ---: |
| 학습 | 10 | 30 |
| 개발 중 내부 확인 | 3 | 9 |
| 내부 테스트 | 3 | 9 |

고정 문자열과 가족 ID의 SHA-256 순서로 배정합니다. 답안 점수·모델 결과를 보고 고르지 않습니다. 같은 부모를 가진 질문 순서/표현 변형은 부모 split을 그대로 사용해야 합니다. 검사기는 같은 부모·가족·실제 응답표가 서로 다른 split에 걸치면 오류를 냅니다. 정정이 다른 가족을 연결한다면 편의대로 배정하지 않고 연결 관계까지 고려한 새 설계가 필요합니다.

**이것은 독립 최종 평가가 아닙니다.** 모든 상황은 같은 합성 제품과 기존 규칙을 사용하고, 값 범위도 개발 과정에서 이미 살펴봤습니다. 이 분할만으로 새 제품·실제 사용자·미노출 도메인에 대한 일반화를 주장하지 않습니다. 독립 제품/규칙 가족과 사람 검토 참조는 별도 과제로 남깁니다.

## 6. 지금 만들어진 것과 다음에 만들 것

이번 산출물:

- `plan.json`: 카드 범위·응답 상태·비용·분할·제외 범위 결정
- `probes.json`: 사람이 읽고 코드로 점검할 수 있는 가상 예시 9개
- `beauty_agent/afa/scenario_plan.py`: 48개 설계 목록 생성, 분할·중복·비용·예시 검사
- `tests/test_afa_scenario_plan.py`: 잘못된 분할·비용·준비 상태 표시가 거부되는지 검사

다음 작업은 **이 설계대로 실제로 질문하고 답을 받는 v2 실행 환경을 만드는 것**입니다. 먼저 기존 엔진이 닫아버린 tools 질문을 별도 v2 adapter에서 안전하게 다루고, 의미 계약과 이벤트 기록을 실제 행동 실행에 연결해야 합니다. 이후에 실행용 응답표를 생성하고, 모든 경로를 검사한 뒤 기존 방식과 비교합니다.

추가 카드·안전 필수 정보의 새 매핑·제품 조회·NLP·후보 확인·v67 변환·실제 앱 연결은 이번 첫 확장 범위 밖입니다. 기존 안전 게이트는 유지하고, 전체 안전 시나리오를 검증했다고 표현하지 않습니다. 학습 step·seed 묶음·모델 선택·통계 비교의 본 protocol은 환경·기준선 검증 후 새 학습 전에 따로 고정합니다. 확장 후에도 기존 방식이 이미 최적이면 그 결과를 그대로 남깁니다.

## 실행 방법과 기록

`cos-agent/`에서:

```powershell
uv run --locked --group rl-train python -m beauty_agent.afa.scenario_plan --report ../../../../outputs/afa-v2-scenario-plan-v1/design.json
uv run --locked --group rl-train pytest -q tests/test_afa_scenario_plan.py
```

기존 출력은 덮어쓰지 않으므로 재실행 시 새 보고서 이름을 사용합니다. 설계 목록의 전체 답은 환경용 설계 자료이며 정책에 넘기지 않습니다. 코드·계획·의미 계약·기존 domain 파일 해시를 보고서에 기록합니다. `development_preview`, `production_enabled=false`, `human_review=unreviewed`, `approved_reference=false`, `training_ready=false`를 유지합니다.

2026-11-17 실행: 48개 설계·16가족·30/9/9 분할과 예시 9개를 확인했습니다. 신규 계획 검사 8개, 전체 실험·RL·PPO 검사 **390개 통과**, 기존 Starlette/httpx 경고 1건입니다. 원본 manifest 27/27, KB 구조 95/95, 현재 명세 검사 371개 통과. 엄격 원본은 62 통과/기존 5 실패, 감사는 52/57과 종료 코드 1을 유지했습니다. coverage 60카드/213분기/180경계와 합성 CLI inactive도 확인했습니다. v1 모델·자료·기존 의미 계약을 보존했으며 새 학습·정책 성능 평가를 수행하지 않았습니다. 보고서는 루트 `outputs/afa-v2-scenario-plan-v1/`에 남겼습니다.
