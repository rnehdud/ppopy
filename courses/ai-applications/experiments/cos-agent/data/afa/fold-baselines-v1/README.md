# 세안 방법을 번갈아 확인한 비교 결과

해당 버전의 실험 기록이다. 현재 에이전트에서 AFA가 맡는 역할은 [목표 구조](../../../docs/agent-runtime-target.md)를 참고한다.

**16개 세안 방법을 모두 번갈아 확인했습니다.** 각 차례에 확인 대상 3개를 빼고 나머지 45개로 답 분포를 새로 만들었습니다. 기존 방식만 비교했고, PPO는 학습하지 않았습니다.

## 결과를 쉽게 보면

질문마다 비용 1을 적용한 결과입니다. 같은 48개 가상 상황이 각 방식에서 한 번씩 확인 대상이 됐고, 무작위 방식은 seed 3개를 반복했습니다.

| 방식 | 평균 질문 수 | 정해둔 종료 기준 |
| --- | ---: | --- |
| 기존 코드의 순서대로 질문 | 4.50회 | 모두 충족 |
| 질문 순서만 무작위 | 3.79회 | 모두 충족 |
| 바로 다음 질문의 효과만 계산 | 4.50회 | 모두 충족 |
| 여러 질문의 순서를 미리 계산 | **3.44회** | 모두 충족 |
| 질문·보류를 모두 무작위로 선택 | 1.17회 | 평균 5.6% 충족 |

미리 계산하는 방식은 기존 순서보다 전체 평균 약 1.06회 덜 물었습니다. 질문·보류를 무작위로 고르는 방식은 대부분 너무 일찍 보류했으므로, 질문 수가 적어도 비용 개선으로 인정하지 않습니다.

### 전체 평균만으로 판단하면 안 되는 이유

| 상황 종류 | 기존 순서 | 질문 무작위 | 여러 질문 미리 계산 |
| --- | ---: | ---: | ---: |
| 손세안 12개 상황 | **4.50회** | 4.50회 | 4.75회 |
| 도구 사용 36개 상황 | 4.50회 | 3.56회 | **3.00회** |

**손세안만 보면 미리 계산하는 방식이 오히려 0.25회 더 물었습니다.** 전체 평균의 이득은 주로 도구 사용 상황에서 나왔습니다. 이 때문에 전체 평균만 보고 모든 상황에서 더 좋은 방식이라고 결론내리면 안 됩니다.

이 표는 미리 구분해둔 구조적 유형을 바탕으로 결과를 나눠 본 기술 진단입니다. 실제 사용자 비율·피로·임상 정확도를 나타내지 않습니다. 도구 종류가 여러 개라 이 가상 자료에서는 도구 사용 상황이 손세안보다 많습니다. 실제 사용자 분포라고 해석하지 않습니다.

## 이번 비교는 지난 비교와 무엇이 다른가?

지난 고정 분할의 내부 확인 9개에는 손세안이 없었습니다. 이번에는 아래 순서를 16회 실행해 빠졌던 조합까지 모두 확인했습니다.

1. 세안 방법 한 묶음의 물 온도별 상황 3개를 확인 대상으로 뺍니다.
2. 남은 45개만으로 답 분포와 계획 계산을 새로 준비합니다.
3. 같은 질문 방식 5개를 뺀 3개에 실행합니다.
4. 다음 차례에는 다른 묶음을 빼고 처음부터 다시 준비합니다.

같은 상황이 다른 차례에서는 준비 자료에 쓰일 수 있습니다. 다만 **자기 확인 차례에서는 같은 세안 방법 전체가 준비 자료에 없습니다.** 원래 파일의 train/val/test 소속과 이번 차례의 준비/확인 역할을 별도로 기록했습니다.

그래서 이번 3.44회와 지난 확인 묶음의 3.00회를 단순 비교해 성능이 나빠졌다고 판단하면 안 됩니다. 준비 자료와 확인 범위가 다릅니다. 옛 고정 분할의 최적 비용 값을 이번 차례별 정책의 최적 비용이라고 주장하지도 않습니다.

## 자료가 섞이지 않도록 한 처리

- `project_fold`가 고정 계획의 ID로 45개 준비 자료와 3개 확인 자료를 분리합니다. 부모·가족이 겹치면 중단합니다.
- 준비 자료는 이번 실험의 train 역할로 표시하고 원래 소속은 `source_split`에 보존합니다. 원본 파일은 고치지 않습니다.
- `TrainModel`에는 그 차례의 준비 자료 45개만 전달합니다. 확인 자료의 역할은 `fold_check`이며 학습 생성자가 거부합니다.
- 새 분포 모델은 매 차례 함수 안에서 생성합니다. 이전 차례의 모델·계획 캐시·체크포인트를 이어 쓰지 않습니다.
- `FoldCheckEnv`는 첫 reset 전에 확인 자료 3개만 연결합니다. 실제 실행·비용·64차원 공개 입력은 기존 환경을 그대로 사용합니다.
- 선택 함수에는 공개 관찰과 마스크만 전달합니다. fold ID·확인 대상 ID·전체 답변표는 전달하지 않습니다.
- 비용 조건과 seed마다 질문 선택기를 새로 만듭니다. 두 비용 조건은 같은 차례의 동일한 45개 분포를 사용하며 비용별 계획은 별도로 계산합니다.
- 모든 방식에 같은 확인 상황을 줬는지 집계 전 검사합니다. 종료 기준을 충족하지 못한 방식에는 비용 절감 수치를 null로 둡니다.

원본의 옛 test_internal 상황도 이 새 순환 실험의 다른 차례에서는 준비 자료에 포함될 수 있습니다. 따라서 손대지 않은 최종 테스트를 유지했다고 표현하지 않습니다. 이번은 이미 살펴본 합성 48개의 내부 순환 점검이며 독립 최종 평가가 아닙니다.

## 미리 고정한 조건과 집계

`protocol.json`에 아래 조건을 실행 전에 고정했습니다. 결과에 맞춘 설정 탐색·추가 학습은 하지 않았습니다.

- 16회 × 확인 상황 3개 × 방식 5개 × seed 3개 × 비용 2조건 = **1,440 episode**.
- 고유 상황은 48개, 세안 방법 가족은 16개입니다. 반복과 차례를 16개 독립 데이터셋으로 세지 않습니다.
- seed는 0/1/2. 기본 질문 비용 1 조건과 마찰·건조 2 조건을 유지했습니다.
- 알고리즘·동률 처리·지지가 없는 상태의 규칙 복구는 기존 `joint_baselines.py` 정의를 재사용했습니다.
- 여러 질문을 미리 계산하는 방식도 실제 답을 미리 보는 것은 아닙니다. 그 차례의 준비 자료 분포와 현재 받은 답을 사용합니다.

### 비용을 다르게 계산한 경우

| 방식 | 기본 평균 질문 수 | 마찰·건조 2 조건의 평균 비용 |
| --- | ---: | ---: |
| 기존 순서 | 4.500 | 6.000 |
| 질문 순서 무작위 | 3.792 | 4.583 |
| 바로 다음 질문 계산 | 4.500 | 3.875 |
| 여러 질문 미리 계산 | 3.438 | 3.875 |

비용 2 조건의 숫자는 질문 횟수가 아니라 미리 정한 가중 비용입니다. 실제 사용자 부담의 측정값은 아닙니다. 두 계산 방식의 질문 수는 비용 조건에서 모두 3.4375회였습니다. 동일한 종료 기준 아래 기존 순서 대비 평균 2.125 비용 단위를 줄였습니다.

기본 조건에서 바로 다음 질문 방식은 총 72회, 여러 질문 계산 방식은 27회 규칙으로 복구했습니다. 비용 변화 조건에서는 각각 0회와 27회였습니다. 이는 선택 시점의 복구 횟수이며 독립 사례 수가 아닙니다. 계산 방식의 결과를 순수한 학습 모델 일반화 점수로 부르지 않습니다. 정상 종료는 기존 의미·실행 게이트의 보호도 포함한 결과입니다.

## 확인한 것과 아직 모르는 것

이번에는 하나뿐인 기본 사용법 일치 손세안 조합까지 자기 확인 차례에서 준비 자료를 제외한 상태로 평가했습니다. 모든 방식의 결과와 질문 경로를 기록했고, 손세안에서 계산 방식의 비용이 증가한 사례도 숨기지 않았습니다.

이 결과만으로 PPO가 더 좋다거나, 계산 방식이 이 순환 평가의 이론적 최적이라고 결론내리지 않습니다. 작은 알려진 규칙 문제에서 직접 계산하는 방식은 여전히 강한 기준선입니다. 다음 PPO 비교에서도 이 기준과 상황 종류별 결과를 함께 봐야 합니다.

현재 한계는 그대로입니다. 모두 같은 합성 제품·기존 규칙·알려진 값 범위를 사용합니다. 사람 검토된 정답·새 제품 가족·실제 사용자 효용·모름/거절을 포함한 본 성능 평가·v67 변환은 아직 없습니다. 새 PPO/BC/SFT 가중치 학습도 하지 않았습니다.

## 재현과 산출물

`cos-agent/`에서:

```powershell
uv run --locked --group rl-train python -m beauty_agent.afa.fold_baselines --report ../../../../outputs/afa-fold-baselines-v1/comparison.json
uv run --locked --group rl-train pytest -q tests rl_tests ppo_tests
```

기존 보고서는 덮어쓰지 않으므로 재실행에는 새 이름을 사용합니다. 실제 결과는 루트 `outputs/afa-fold-baselines-v1/`에 있습니다. 비교 보고서에는 준비·확인 ID, 차례별/seed별 지표, 복구 수, 모든 질문 경로, 코드·입력 해시를 기록합니다. 결과로 설정을 고르지 않았고, 전체 실행의 모델 재구성 수는 16개입니다.

`development_preview`, `production_enabled=false`, `human_review=unreviewed`, `approved_reference=false`, `independent_evaluation=false`를 유지합니다. 기존 자료·모델·이전 비교 보고서는 보존합니다.

## 실행 확인 — 2026-11-17

16개 묶음·48개 고유 상황·두 비용 조건에서 1,440 episode를 완료했습니다. 하나뿐인 기본 사용법 일치 손세안 가족도 그 확인 차례에서는 준비 자료에서 제외했습니다. 새 검사 10개와 전체 실험·RL·PPO 검사 **456개 통과**, 기존 Starlette/httpx 경고 1건입니다.

원본 manifest 27/27, KB 구조 95/95, 현재 명세 검사 371개 통과. 엄격 원본은 62 통과/기존 5 실패, 감사는 52/57 및 종료 코드 1 유지. coverage 60카드/213분기/180경계와 합성 CLI inactive 확인. 이번에는 신경망·PPO 가중치를 학습하지 않았습니다.

결과는 루트 `outputs/afa-fold-baselines-v1/comparison.json`, 손세안/도구 사용별 기술 진단은 `subgroup-diagnostics.json`, 재현·보존 확인은 `verification-index.json`입니다. 원래 fold-plan의 미실행 표시는 계획 작성 당시 기록으로 남기고, 이번 실행 여부는 이 새 protocol과 보고서에 기록했습니다.
