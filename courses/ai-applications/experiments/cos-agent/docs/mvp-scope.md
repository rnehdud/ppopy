# 범위와 개발 순서

현재는 **설계 단계**입니다. [프로젝트 개발 가이드](project-guide.md)를 우선 읽습니다. 아래 기능과 순서는 후보 로드맵이며 한꺼번에 구현할 작업 목록이 아닙니다. 각 단계의 작은 목표를 정한 뒤 진행합니다.

## 이번 초기 골격

- 공통 입력/출력 계약과 FastAPI 문서
- 합성 제품 2개, 확인/버전/명시적 제외 조건 검사
- 추가 질문 또는 아침/저녁 초안; 내용 hash와 합성 근거 ID
- 모델 없는 기준선과 선택형 Ollama 질문 선택 adapter
- 계약·보류·실패 경로 회귀 검사, 의존성 lockfile

## 다음 작업 — 순서대로

1. 앱 adapter: 기존 `CareAnalysisRequest` → 버전이 있는 공통 입력. 같은 합성 사례로 기존 엔진과 결과 의미 비교.
2. 프로필·제품 도구: 인증된 서버 사용자 문맥, 수동 확인 카탈로그, 정확한 제품 버전/표시 사용법/출처 조회. 실제 데이터와 합성 자료 분리.
3. 루틴 승인/저장: PostgreSQL migration, 사용자 소유권, 초안 hash/만료/기반 버전, 수정 후 재승인, idempotency와 동시 수정 충돌 검사. 현재 hash를 승인 증명으로 사용하지 않음.
4. Single-Agent 확대: 문진 추출 후보 → 사용자 확인, 읽기 도구 선택. 규칙 엔진 결과와 근거 범위 내 설명. 쓰기 도구는 서버의 승인 검사 후에만 실행.
5. 지속 관리: 사용 기록·불편감 직접 기록, 시간대·발생/저장 시각, 7일 요약·수정 제안. 자동 승인 금지.
6. 평가 후 SLM 선택/학습: 기준선 실패 분류, 사람 정답 확보, 모델 태그/프롬프트 고정, 분리된 데이터로 학습 전후 비교.

각 단계가 실제 API·UI·저장소에서 검증되기 전 Linear의 완료로 표시하지 않습니다. 이번 작업은 ERI-13/14 전체 구현이 아닙니다. 날씨·바코드/OCR·검색 RAG·스마트미러 음성·알림은 핵심 흐름 이후 확장합니다. OCR이 필요하면 제품 포장/라벨 확인에 한정합니다.
