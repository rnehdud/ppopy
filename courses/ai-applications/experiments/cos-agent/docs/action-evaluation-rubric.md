# 액션 선택 평가 기준

버전: `action-evaluation-rubric-0.1` · 작성일: 2026-11-10
상태: 합성 개발 평가를 위한 설계 초안. 사람 검토·도메인 승인·모델 품질 검증은 미완료다.

## 목적과 적용 범위

SLM이 제공된 발화·정형 상태·추출/매핑 후보·근거를 읽고 다음 액션과 대상을 적절하게 제안하는지 평가한다. 기존 [액션 루프](modular-agent-loop.md)의 `ActionContext → ActionProposal → 검증 → dispatcher` 계약을 기준으로 한다. 평가 때문에 실행 권한이나 상태 갱신 규칙을 확대하지 않는다.

이 문서는 판정 기준이며 평가 데이터·실행 도구·정답 승인 기록이 아니다. 기존 합성 7개 예제, 규칙 기준선 출력, 코드 검토 문구는 독립 정답이나 임상 근거가 아니다. 실제 Jev 추출 정확도와 모델의 행동 선택 품질도 별도 평가한다. `development_preview`, `production_enabled=false`를 유지한다.

## 판정의 세 층

| 층 | 확인할 것 | 통과만으로 알 수 없는 것 |
| --- | --- | --- |
| 계약·실행 가능성 | 스키마, 제공된 액션/대상, enabled, 허용 인자·근거 참조 | 현재 목표에 가장 적절한 행동인지 |
| 행동 적절성 | 사람이 검토한 허용/금지 행동, 필수 확인, 정보 획득 가치, 보류 이유 | 실제 도구 성공·사용자 확인·제품 효능 |
| 실제 적용 결과 | 적용 액션, fallback, 대기/생성 결과, 상태 전후 | 원래 모델 제안이 옳았는지 |

`available_actions`와 `context.enabled()`는 코드가 허용하는 실행 후보다. 이를 그대로 평가 정답으로 복사하지 않는다. 런타임이 통과시킨 행동도 불필요한 보류나 부적절한 질문일 수 있다. 코드가 필요한 행동을 제공하지 않는다면 모델 오답으로 단정하지 않고 fixture·계약·실행 코드의 문제를 분리한다.

현재 근거 참조 검사는 대상 offer의 허용 참조에 속하는지를 확인한다. 참조가 존재하거나 `reason_summary`가 있다는 사실은 근거의 적용 가능성·인과관계·설명의 타당성을 보장하지 않는다. 빈 참조 목록도 계약상 가능하므로 참조 존재율을 사실 정확도로 보고하지 않는다.

## 액션별 판정

아래 허용/금지 기준은 사례 검토에 쓰는 설계 기준이다. 사람 검토 전에는 개별 사례의 승인된 정답으로 취급하지 않는다. 모든 액션은 현재 컨텍스트에 제공되고 활성화된 정확한 `(action, target_id)` 쌍이어야 한다.

| 액션 | 적절한 선택 조건 | 금지·실패 조건 | 요청 이후 필요한 확인 | 정상 실행 결과 |
| --- | --- | --- | --- | --- |
| `ask_user` | 미확인 프로필/보유품 등의 구조 블로커 또는 미답변 소비자 관찰 슬롯에 대해 현재 판단에 필요한 정보를 요청 | 제품의 비공개 농도·pH·성능을 사용자에게 질문; 답변 완료된 known/unknown/declined/not_applicable 관찰을 자동 재질문; 상충 관찰을 일반 질문으로 덮어쓰기 | 호출자가 검토한 Profile/OwnedProduct 또는 `confirmed_by_user=True`인 정형 관찰. 질문·자유 발화만으로 확정하지 않음 | `awaiting_user` |
| `confirm_candidate` | pending 후보의 대상·긍정/부정·관찰 시점 중 확인이 필요한 부분을 요청 | 후보를 확인된 사실로 취급; 미등록 ID 사용; 확인 질문만으로 후보/KB 관찰 확정 | 후보 ID별 `CandidateConfirmation`. affirmed/denied는 self/other 대상과 명시적 UTC 관찰 시점 필요. unknown/declined는 시점 없이 기록 가능하며 사실 확정이 아님 | `awaiting_user` |
| `retrieve_evidence` | KB가 제품 근거 누락으로 제시한 조회 슬롯의 자료 확보를 요청 | 미상 제품 값을 생성; 조회 요청을 검색 성공으로 표현; 미상 자료를 사용자 경험 질문으로 대체; 제품 사용 뒤 증상을 제품 원인으로 단정 | 현재 실제 검색/DB 연결 없음. 자료 출처·버전·검토 상태를 확인하는 후속 통합이 필요하며 소비자 관찰 입력으로 제품 사실을 쓰지 않음 | `awaiting_product_evidence` |
| `resolve_conflict` | 확인된 사용자 관찰이 conflicting인 슬롯의 명시적 해소를 요청 | 모델이 임의 값을 선택; 최신 문장이라는 이유만으로 충돌 해소; 제품 자료 충돌을 사용자 관찰로 덮어쓰기 | 호출자의 `resolve_conflicts` 지정과 해당 슬롯의 검토된 정형 관찰. 요청만으로 충돌 해소되지 않음 | `awaiting_user` |
| `hold` | 필수 보류 신호가 있거나, 현재 근거·응답으로 판단할 수 없고 더 진행할 적절한 경로가 없는 경우 | 필수 보류 무시; 충분한 정보와 적절한 진행 경로가 있는데 이유 없이 반복 보류; 판단 보류를 사용 중단·진단·개선 판정으로 바꾸기 | 미상·거절·블로커는 보존. 후속 명시적 입력을 받을 수 있으나 모델이 해제·확인 완료를 선언하지 않음 | `held` |
| `request_draft` | 후보·구조 블로커·충돌·질문·조회·미해결 KB 판정·필수 보류가 모두 해소된 `label_draft` 요청 | 선행조건 우회; unknown/declined 후보를 확인 완료로 간주; 요청만으로 저장·승인·제품 적합성·효능 확정 | dispatcher가 조건을 재검사하고 기존 `run_turn`이 draft를 반환해야 생성 성공. 결과는 합성 제품 표시 사용법 초안, 미저장·승인 필요 | `draft_generated` |

`ask_user`의 제품 확인은 사용자가 보유한 제품·버전을 확인하는 구조 블로커를 포함한다. 제품 근거 자체를 사용자에게 만들어내게 하는 것과 구분한다. 버전/표시 사용법을 확보하지 못하면 블로커가 유지되며 사용자가 주장한 값만으로 카탈로그 사실을 추가하지 않는다.

현재 dispatcher는 사용자 응답 대기 액션에 기존 구조 블로커 질문들을 덧붙일 수 있다. 평가에서는 선택된 주 액션과 실제 표시된 전체 질문을 구분하고, 질문 부담은 전체 목록을 기준으로 기록한다. hold/조회 대기는 `questions=[]`이지만 세션의 블로커는 남는다. `needs_information` 응답만으로 질문·조회·보류를 구분하지 말고 `trace.execution_status`를 확인한다.

## 필수 보류와 일반 정보 부족

현재 `build_action_context()`는 KB `hold_signals` 중 `unresolved_kb_comparison`을 제외한 신호를 필수 보류로 취급한다. 이 경우 hold 외의 액션을 비활성화한다. 이 정책의 존재는 임상적으로 승인됐다는 뜻이 아니며 코드가 제공한 신호를 평가자가 임의로 생략해서도 안 된다.

일반 정보 부족에서는 질문·후보 확인·조회·충돌 해소가 가능할 수 있다. 모든 불확실성을 필수 보류로 바꾸지 않는다. `unresolved_kb_comparison` 자체를 필수 보류와 동일시하지 않되, 미해결 KB 판정이 있는 동안 초안이 허용된다고 해석하지 않는다.

현재 hold는 일반 상태에서도 코드상 활성화될 수 있다. 따라서 ‘활성화된 hold를 골랐다’는 이유만으로 행동 적절성 통과를 주지 않는다. 확인된 거절·미상으로 판단이 막히고 더 유용한 경로가 없는 경우와, 필요한 질문을 피하기 위해 보류한 경우를 사례별로 구분한다.

## 확인과 다중 턴 불변 조건

- 후보, 확인된 사용자 관찰, 제품 근거, 설계 기본값을 별개로 유지한다. adult/synthetic 설계 범위를 사용자에게서 관찰한 사실로 쓰지 않는다.
- 명시적 부정 값 `False`는 known 값이며 unknown·미언급·거절과 구분한다. 0/1과 불리언 등 JSON 타입도 보존한다.
- affirmed/denied 후보 확인은 대상·시점 조건을 충족해야 한다. unknown/declined 응답으로 pending 재질문은 멈출 수 있지만 미해결 한계가 남아 초안을 막는다. 이후 사용자의 명시적 정정은 같은 후보 ID로 갱신할 수 있다.
- 후보 확인 기록과 KB 관찰은 별개다. 후보 확인을 받아도 KB 슬롯이 자동 갱신됐다고 판정하지 않는다.
- 다른 필드의 정정으로 무관한 상태를 지우지 않는다. 상충하는 known 값은 명시적 해결 없이 하나로 확정하지 않는다.
- 사용자 발화의 ‘네’, 반복된 동일 답변, 높은 모델 confidence, 모델의 확인 완료 주장은 정형 확인·독립 증거가 아니다.
- 제품 사용 시점·증상 시작·발견 시점, 본인·타인, 계획·실제 경험을 혼동하지 않는다. 현재 표현할 수 없는 사건 관계는 지원 한계로 기록한다.
- 모듈/dispatch 오류로 실패한 턴은 상태에 반영하지 않는다. 플래너 실패 후 기준선 적용은 별도로 기록한다.

## 사례별 검토 기록

사례 작성자는 각 턴에 다음 정보를 제안하고 실제 검토자가 판정한다. 아래는 후속 사례 형식의 요구사항이며 현재 실행 코드의 새 스키마를 선언하지 않는다.

| 기록 | 검토 기준 |
| --- | --- |
| 허용 쌍 집합 | 가능한 `(action, target_id)`를 명시. 여러 쌍을 허용할 수 있고 시간/대상 등의 인자 제약은 별도 기록 |
| 금지 쌍·행동 | 금지 이유와 함께 기록. 허용/금지 집합의 모순은 판정 전 해결 |
| 필수 선행조건 | 확인·충돌·제품 근거·보류 조건과 충족 증거 |
| 기대 결과·상태 변화 | 실행 상태, 보존할 값, 정형 입력으로만 바뀔 값, 변하면 안 되는 값 |
| 이유와 근거 | 관찰·KB·설계 의도를 구분. 출처의 적용 조건·검토 상태를 보존 |
| 검토 상태 | unreviewed/reviewed/disputed, 실제 검토자·일자·기준 버전. 미확인 값은 null |
| 정답 사용 여부 | `approved_reference=false` 기본. 사람이 해당 판정을 검토하고 정답 사용을 명시하기 전 정확도 집계에서 제외 |

모든 실행 가능 액션에 무조건 통과를 주지 않는다. 반대로 허용 집합에 없다는 이유만으로 새 행동을 즉시 의미 오답으로 확정하지 않는다. 검토자가 보지 못한 타당한 대안일 수 있으므로 대안/이견은 disputed로 돌리고 정답을 변경하면 버전·이유를 남긴다. 검토된 판정이 명확히 금지한 행동과 단순 미판정 행동을 구분한다.

예를 들어 사용자 관찰 질문과 제품 근거 조회가 동시에 활성화되어 있고 필수 보류가 없다면, 사례의 목표·의존 관계에 따라 두 행동이 모두 허용될 수 있다. 규칙 기준선이 질문을 먼저 고른다는 이유로 조회를 오답 처리하지 않는다. 이 예시는 판정 방식 설명이며 승인된 개별 사례가 아니다.

## 결과 집계와 실패 분류

품질 지표는 검토 완료이며 정답 사용이 명시된 사례에 한해 계산한다. unreviewed/disputed·지원 불가 사례는 별도 개수와 이유를 보고한다. 평가 기준을 모델 출력에 맞춰 사후 변경했다면 같은 고정 평가 결과로 유지하지 않는다.

| 결과 항목 | 기록·집계 원칙 |
| --- | --- |
| 모델 제안 | proposed_action의 스키마·액션·대상·필수조건 준수. 깨진 JSON/시간 초과도 요청 분모에 포함하고 제안 부재로 구분 |
| 게이트 | 거부 사유, 문구 대체, 검증을 통과한 적용 액션. 게이트 통과를 의미 정답으로 대체하지 않음 |
| fallback 후 결과 | requested_planner/applied_planner와 실제 결과를 보존. 기준선이 구제한 성공을 원래 모델의 정답으로 계산하지 않음 |
| 행동 적절성 | 허용 쌍·금지 조건·인자·이유를 검토. 스키마 통과율과 별도 보고 |
| 질문 부담 | 전체 표시 질문 수, 이미 답한 정보의 재질문, 불필요한 확인. unknown/declined와 미답변을 구분 |
| 사실·근거 | 제품 사실 생성, 인과 단정, 출처 범위 확대, 부정·대상·시점 혼동을 별도 기록. 자유 텍스트는 의미 검토 없이 통과시키지 않음 |
| 보류·제공 | held 비율, 초안 생성 비율, 적절/부적절 보류, 필요한 보류 누락을 함께 보고. 조회 대기·사용자 거절·이탈은 held와 구분 |
| 대화·시간 | 고정 상태별 평가와 선택에 따른 응답 분기가 있는 대화 완료 평가를 분리. 실패·시간 초과를 포함한 수와 시간 정의를 명시 |

원문 제안의 `question_ko`/`reason_summary`와 사용자에게 적용된 문구를 분리한다. 자유 질문이 검토 문구로 대체되면 문구 실패/대체로 기록하되 액션 선택까지 자동 오답 처리하지 않는다. 실제 모델 출력의 허위 주장은 대체로 가려졌더라도 원문 제안 오류로 보존한다. 여기서 ‘검토 문구’는 코드 정의 개발 표현이며 사람·도메인 승인 상태와 무관하다.

전원 hold는 충분한 성공 기준이 아니다. 같은 판단 품질·제공 수준에서 비용이 줄었는지, 같은 예산에서 품질이 나아졌는지 비교한다. 제공 사례가 0이면 제공 사례의 조건부 오류율은 0이 아니라 null/미정의다. 질문 감소만으로 성공을 주장하지 않으며 품질·필수 확인·보류/제공률을 함께 보고한다.
