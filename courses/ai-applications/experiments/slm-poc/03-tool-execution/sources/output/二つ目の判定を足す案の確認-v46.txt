既存の二つ目の判定器を足す案の確認（V46）
2026-11-09

結論
「Aが候補を出し、Bが今それを実行すべきか判定すれば直る」という私の直前の案は、この既存部品の接続では成り立たなかった。採用しない。
未確認のBを、正しく判定するものとして説明していたことが問題だった。

実際に使ったもの
A: V45の追加学習後の重み。
B: 以前のV29通常追加学習の重み。候補ツールの説明を付けたyes/noの判定器。
AもBも同じ実際の状況を読む。ただしBが以前学習した入力の書式と、今回のV41由来のflat書式は異なる。
以前からの閾値を固定し、8例を見てから質問・閾値・重みを変更しなかった。
各例は、以前から使っている同じメモの道具と内容。読み取り・追記の履歴は実際のローカルハンドラーで作った。
「もう一度読む」という追加依頼も含めた。正解ラベルや期待するツール順はモデルへ渡していない。

正しい次の選択 / Aだけ / AとB
読む前: 読む / 追記 / 追記。
読んだ後: 追記 / 追記 / 追記。
追記した後: 呼ばない / 追記 / 追記。
読むだけの依頼を読み終えた: 呼ばない / 呼ばない / 読む。
追記後に再読する依頼: 読む / 追記 / 追記。
最初に必要な読み取りツールがない: 呼ばない / 追記 / 追記。
読んだが追記ツールがない: 呼ばない / 呼ばない / 読む。
挨拶: 呼ばない / 呼ばない / 読む。

Aだけでは4/8。Bを加えると1/8。
Bは追記済みの場面でも追記を許可した。読むだけの依頼で正しく止まっていたAを、再読へ変えてしまった例もあった。
Bが全候補を断った場合も、それだけで依頼全体の完了と呼ばない設計にした。

確認の限界
これは一種類の道具の8つの途中状態で、最初から最後まで自動で動かした成績でも、新しい独立した会話の精度でもない。
今回の入力への学習をしていない既存Bをつないだ確認である。二段方式全般が不可能という証明ではない。
今回の結果を直すための追加学習や、閾値調整はしていない。デモ・既存コード・重みも変更していない。
