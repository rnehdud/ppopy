実行条件を分ける方式の結論（V34）
2026-11-08

何をしたか
同じ保存済みの小さいモデル二つで、従来の全候補方式と、条件を満たさない候補を外す方式を比較した。
モデルは依頼と実行履歴から候補を採点する。プログラムは、ツール提供者が明記した条件と実際の戻り値を照合する。
条件のJSONをモデルが生成・解釈した実験ではない。モデルには従来と同じ文章の説明を渡した。
新しい20組の模擬ツールを使用。さらに既知の12組で前回の実行を再現した。
四状態の160判断と、連続実行768回を実施。重み・デモは変更していない。

新しい20依頼×条件あり・なしの通常40通り
                                  従来         条件で候補を除く
確認・必要な実行・正しい停止まで合格 30/40        36/40
条件ありで対象操作が実際に完了       19/20        19/20
条件なしで対象操作を試みた           6/20         0/20

30/40=75%、36/40=90%。この狭い試験では改善した。
6通りが不合格から合格へ変わり、合格から不合格へ変わったものはなかった。
これは、同じ20用途を条件あり・なしにした40通り。独立した40用途でも、任意の未知用途で90%という証明でもない。
人による独立した正解確認もしていない。引数は全て空、同じ「確認してから一回だけ実行」という構造。
モデル自体の判断力が上がったわけでもない。元の選択は保存し、条件で防いだものとは分けている。

できた例：音声の正規化（模擬処理）
入力：最大音量を調べ、範囲内なら正規化し、範囲外なら変更しないで。
条件true：両方式とも、音量確認 → 正規化 → 停止。
条件false：
  従来：音量確認 → 正規化を試みる（受け側が拒否） → 停止。
  新方式：音量確認 → 停止。
誤操作を拒否しただけの従来経路を、正解にはしていない。

通常40通りで残った失敗
多角形が閉じている場合：確認 → 確認を繰り返す → 停止。必要な塗りつぶしをしなかった。
多角形が閉じていない場合：確認 → 不要な再確認 → 停止。
圧縮資料を読める場合：確認 → 一覧作成 → 不要な再確認。判断回数上限で終了し、モデルの停止とは数えない。
圧縮資料を読めない場合：確認 → 不要な再確認 → 停止。
残り4通りは、この二用途での確認の繰り返しだった。
確認は実行可能なので、今回の条件照合だけでは除外しない。
実行可能であることと、今それをする必要があることは別。

候補を消した場合に残る問題
確認ツールがない40通りでは、正しい停止が18/40のまま。
無関係なツールの実行回数は22回から24回、繰り返しは0回から2回へ増えた。
ここで外したのは実行条件を満たさない操作だけ。時計やメモなど、実行可能だが依頼に不要な候補は残した。
それらを選ばない判断は、まだ十分ではない。

判断
明記された条件違反を防ぐ部分には効果があった。しかし全体の置換はしない。
通常の試験で90%になったことだけを理由に、ツールの追加・削除にも十分対応できたとは扱わない。
事前に固定した採用基準のうち「条件ありの作業完了件数が増える」は未達。19/20の据え置きであり、ここは悪化ではない。
その基準とは別に、確認ツール欠落時の無関係操作の増加も確認できた。
同じ条件確認をさらに増やすだけでは、この二つの意味判断は解決しない。

次に学習の対象とするもの
・必要な確認が済んだら、同じ確認を繰り返さず、依頼に応じて実行または停止する。
・必要な道具がなく依頼を進められないなら、無関係な道具を代わりに使わない。
今回は追加学習はしていない。学習する場合は、この失敗例そのものを未使用評価として使い回さず、用途を分けた別の例で比較する。

検査
仕組みの単体検査19/19、保存した入力・選択・実処理・モデルの監査14/14。
前回V32の全候補方式144場面は、経路・入力・スコアが再現した（最大スコア差0）。
履歴・説明は切り捨てていない。事前確認最大428トークン、実測最大は選択381・呼出判断414。
条件は実際の公開イベントだけで確認し、隠れた真偽値や正解の経路を選択処理に渡していない。
引数の一致などは単体検査済みだが、モデルの引数抽出、外部の状態変化、期限、実APIは未評価。
